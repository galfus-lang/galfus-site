- **Package Manager**: bun
- **Add-ons**: prettier, tailwindcss, sveltekit-adapter, mcp

You are able to use the Svelte MCP server, where you have access to comprehensive Svelte 5 and SvelteKit documentation. Here's how to use the available tools effectively:

## Available Svelte MCP Tools:

### 1. list-sections

Use this FIRST to discover all available documentation sections. Returns a structured list with titles, use_cases, and paths.
When asked about Svelte or SvelteKit topics, ALWAYS use this tool at the start of the chat to find relevant sections.

### 2. get-documentation

Retrieves full documentation content for specific sections. Accepts single or multiple sections.
After calling the list-sections tool, you MUST analyze the returned documentation sections (especially the use_cases field) and then use the get-documentation tool to fetch ALL documentation sections that are relevant for the user's task.

### 3. svelte-autofixer

Analyzes Svelte code and returns issues and suggestions.
You MUST use this tool whenever writing Svelte code before sending it to the user. Keep calling it until no issues or suggestions are returned.

### 4. playground-link

Generates a Svelte Playground link with the provided code.
After completing the code, ask the user if they want a playground link. Only call this tool after user confirmation and NEVER if code was written to files in their project.

## Styling and Responsiveness:

- **Container Queries**: ALWAYS use container queries (`@container`, `@md`, `@lg`, etc.) for responsive design. NEVER use media queries (`sm:`, `md:`, `lg:`, etc.).

## Shared data and SurrealDB

- `packages/data-manager` is the single source of truth for the shared
  SurrealDB schema, generated record types, input validation, queries, and
  transactions. Do not create app-local schema files or repositories for a
  shared table.
- Applications own their `Surreal` connection and pass it to functions from
  `@galfus/data-manager/server`. Do not move connection configuration, HTTP
  responses, redirects, cookies, or JWT handling into `data-manager`.
- Use `@galfus/data-manager` for generated record types and Valibot input
  schemas. Every data-manager query/transaction must accept `unknown` input,
  validate it with Valibot, and use only the parsed output. This normalizes
  data and removes unrecognised fields before any query is made.
- Put persisted table definitions only in
  `packages/data-manager/database/modules/*/schema/*.surql`. Keep files to
  `DEFINE` statements; use parameter bindings for all query values.
- `packages/data-manager/src/generated/index.ts` is generated by SurrealKit.
  Never edit it manually; commit its changes after a schema change. Valibot
  schemas validate operation inputs and must not duplicate persisted record
  definitions.
- The exported generated table types describe complete records. For `SELECT`
  projections or `FETCH` results, derive a local `Pick<T, ...>` result type
  instead of recreating a table interface.
- Before any schema sync, run the matching dry-run. `sync` can prune managed
  definitions that no longer exist in source files:

  ```sh
  bun run db:local:check
  bun run db:local:sync
  bun run db:local:typegen
  ```

- Cloud targets require their scoped environment variables and must remain
  explicit. Never use a local target to reach cloud infrastructure:

  ```sh
  bun run db:dev:check
  bun run db:dev:sync
  bun run db:dev:typegen

  bun run db:prod:check
  bun run db:prod:sync
  bun run db:prod:typegen
  ```

  Development reads `SURREALDB_DEVELOPMENT_*`; production reads
  `SURREALDB_PRODUCTION_*`. Do not print secrets or add them to source control.

## Internationalisation

- `packages/i18n` owns all user-facing messages. Add a group to the base
  locale under `src/dictionaries/en-US/` and compose it in `en-US/index.ts`;
  then add the same group and shape to every locale. TypeScript rejects
  missing or misspelt entries.
- Use dotted, grouped IDs such as `error.auth.pass.password_dont_match` and
  `error.fields.email.malformed`. Keep data-manager errors as IDs, never as
  human-readable strings.
- `data-manager` may expose Valibot issues for diagnostics, but consumers must
  render `error.id` (or `messageIdFromIssues`) through `translate(...)` at the
  application boundary. Applications choose the locale; data-manager does not.
- `translate(...)` uses FormatJS and ICU Message syntax. Pass placeholder
  values as its third argument; never add manual string interpolation to
  dictionaries or consumers.
- Do not edit a translation to change validation behaviour. Validation IDs are
  defined by the Valibot input schema; dictionaries only provide locale text.
